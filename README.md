### Чи буде втрата даних?

(У експерименті використовувалось **backup-count: 1** — у кожної партиції є лише одна репліка окрім primary.)

- **Відключення однієї ноди:** втрати **немає**. При backup-count 1 кожна партиція має 2 копії (primary + 1 backup) на різних нодах; коли одна нода виходить, на інших залишається копія — дані зберігаються.

- **Відключення двох нод послідовно:** втрата даних **можлива** (і як видно на скріншоті, вона сталася). У кожної партиції лише 2 копії (primary і один backup). Після виходу двох нод залишається одна — вона тримає тільки ті партиції, у яких була primary або backup. Партиції, у яких обидві копії були на двох вимкнених нодах, втрачаються.

- **Відключення двох нод одночасно (kill -9):** втрата даних **можлива** (і справді трапилася) з тієї ж причини: якщо для партиції і primary, і єдиний backup були на двох впалих нодах, ці дані втрачаються.

### Яким чином зробити щоб не було втрати даних?

При **backup-count: 1** витримується лише відмова однієї ноди. Щоб не втрачати дані при падінні двох нод:

1. **Збільшити `backup-count` до 2** (або більше) — тоді кожна партиція матиме три копії (primary + 2 backup) на різних нодах, і при виході двох нод копія залишиться на третьій.
2. **Тримати кількість нод більшою за кількість копій** (наприклад, мінімум 3 ноди при backup-count 1 для безпечного виходу однієї ноди; при backup-count 2 — більше нод для безпечного виходу двох).
3. **Використовувати синхронні бекапи** (`backup-count`), щоб запис підтверджувався лише після збереження репліки.
4. **Увімкнути persistence (MapStore)** — дані пишуться на диск; після перезапуску нод мапу можна відновити з хранилища і не покладатися лише на in-memory репліки.

## Distributed map with optimistic lock

```bash
python hazelcast_demo/write_optimistic.py 
Final value for 'key': 30000
Time taken (optimistic lock): 15.105s
```

З оптимістичним блокуванням результат також 30_000, як і очікувалось. Швидкість залежить від кількості конфліктів (retry).

## Порівняння

 Режим              | Кінцеве значення для "key" | Втрата даних? | Час (ваш вимір) |
|--------------------|----------------------------|----------------|------------------|
| Без блокувань      | < 30_000 (13387) | Так           | 7.212s        |
| Песимістичний lock | 30_000                     | Ні            | 14.241s          |
| Оптимістичний lock | 30_000                     | Ні            | 15.105s |


- **Чи однакові результати для песимістичного та оптимістичного підходу?**  
  Так: обидва дають 30_000, втрати даних немає.

- **Песимістичний чи оптимістичний підхід працює швидше?**  
  При низькій конкуренції оптимістичний часто швидший (менше накладних витрат, рідкі retry). Проте у такому випадку, як у нашому прикладі, де є висока конкуренція (3 потоки, один ключ), багато retry у оптимістичного варіанту може призвести до часу, що може бути порівнянний або навіть більший за песимістичний.  


## Bounded queue


```bash
python hazelcast_demo/bounded_queue.py
Reader 2 read value: 1
Writing 1
Reader 1 finished
Writing 2
Reader 2 finished
Writing 3
Writing 4
Writing 5
Writing 6
Writing 7
...
Writing 99
Writing 100
Writer finished (sentinel -1)
Bounded queue demo done.
```

Бачимо, що черга заповнюється по одному елементу за раз. Обидва читачі працюють з однією й тією самою distributed-чергою demo_queue:
- Кожен виклик take() атомарно забирає один елемент з черги (FIFO).
- Хто перший викликає take() на кластері — той і отримує наступний елемент.
Тому два клієнти конкурують за елементи: кожне значення потрапляє рівно одному з двох читачів. Порядок між ними не фіксований (наприклад: Reader 1, Reader 2, Reader 1, Reader 2 тощо).
- Poison pill (-1): коли один читач отримує -1, він кладе -1 назад у чергу (my_queue.put(-1)), щоб другий читач теж отримав -1 і коректно завершив роботу.
Підсумок: значення вичитуються по одному на один виклик take(), розподіл між двома клієнтами — через конкуренцію за take() на спільній черзі.
